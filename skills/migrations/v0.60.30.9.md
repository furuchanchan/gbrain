# v0.60.30.9 — loops_close expires commitment facts through the coordinator (#5869)

On a managed brain, `gbrain loops done|drop` (the `loops_close` op) ran
`UPDATE facts SET expired_at = now()` directly. The `managed_writer_guard`
trigger refuses any facts write outside the coordinator's
`gbrain.write_sources` capability, so the statement raised
`writer_coordinator_required`, the catch-all best-effort block swallowed
it, and the op returned `fact_expired: true` anyway. Every commitment
fact projected by a closed loop stayed active — entity cards kept
carrying promises the owner had already settled or dropped.

The expire now runs the same way `forget_fact` reaches the table: inside
a transaction, under `withCoordinatedWrite` scoped to the fact's own
source. Unmanaged brains keep the direct update (the guard is inert when
`persistence_brain.enabled` is false). `fact_expired` reports the real
outcome — a fact that was already expired or a failed expire no longer
reads as success — and a failed expire names itself in
`fact_expire_error`.

Facts left active by earlier closes need one `gbrain forget_fact <id>`
each; there is no bulk repair in this release.
