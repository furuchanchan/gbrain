# Upgrade to v0.60.52.3: apply-migrations no longer refuses its own lease

On Postgres, `gbrain apply-migrations` could stop with `migrations_running`
naming the runner's own pid when the `gbrain_cycle_locks` lease row stopped
matching the handle the runner held (fence/acquisition-token rewritten
between acquisition and the re-check). The lease re-check now treats a live
row bearing the process's own pid+host as still-owned — the row could only
have been written by that process — re-binds the handle to the row's current
fence/token, and proves ownership with one fenced refresh. A row held by a
different pid or host still refuses as before.

Nothing to do: the fix is in the runner itself. If a brain was wedged on
`migrations_running` naming its own pid, re-run `gbrain apply-migrations --yes`.
