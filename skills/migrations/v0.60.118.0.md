# Upgrade to v0.60.118.0: a `gbrain dream` no longer races autopilot on the brain-wide phases

A nightly `gbrain dream` derives its source id from the brain directory
(`default` on most installs) and used to take the per-source cycle lock
`gbrain-cycle:default`, while `gbrain autopilot`'s global maintenance holds
the legacy `gbrain-cycle` row. Both ran at once, and the brain-wide phases —
synthesize, patterns, grade_takes and friends — executed twice concurrently
on the same rows: double LLM calls, journal conflicts, and a `SYNTH_PHASE_FAIL`
for a page the other run had just advanced.

The cycle lock now follows the resolved phase set, not the source id: a run
whose phases include any mixed- or global-scoped phase takes the shared
`gbrain-cycle` lock, so a dream and an autopilot run serialize instead of
overlapping. A purely source-scoped cycle (`gbrain dream --source <id>`, or an
explicit `--phase` list of source-scoped phases) keeps its per-source lock, so
different sources' freshness cycles still overlap — including alongside the
autopilot's global maintenance.

1. **Finish the upgrade.** `gbrain upgrade` runs it; no schema migration is
   added. Restart every `gbrain serve`, autopilot and worker so no old-binary
   scheduler keeps taking the per-source lock for brain-wide work.

2. **Keep both schedulers.** `gbrain dream` and `gbrain autopilot` are meant
   to coexist: on a multi-source brain the autopilot does not run the
   per-source background phases, so the nightly dream stays required. They
   now serialize on the shared lock rather than fighting — a run that finds
   the lock held skips with `cycle_already_running`, same as always.

3. **Nothing to change in your cron.** Existing schedules keep working; the
   only behavioral change is that a bare `gbrain dream` and an autopilot
   maintenance run can no longer overlap their brain-wide phases.
