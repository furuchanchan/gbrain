# v0.60.10.1 Migration Notes

## What changed

- **Autopilot freshness loop skips connector-managed sources.** Sources with
  `config.kind` `google` or `github` legitimately carry a `local_path` (their
  connector-managed root). The freshness loop previously submitted a legacy
  `sync` job carrying that path as `repoPath` for every such source every
  cycle — jobs `assertManagedFilesystemWrite` always refuses. Connector
  sources now skip the loop; their sync flows through the managed
  `connector-sync` job as before.

- **`gbrain sources set-path <id> --clear` (alias `--null`)** resets a
  connector-managed source's `local_path` to NULL — the supported repair for
  a stale connector root, which previously had no remedy short of editing the
  DB. Refused for filesystem sources (exit 6; repoint with `set-path <id>
  <path>`) and while a `persistence_source_bindings` row for the source's
  current incarnation still verifies against the path (exit 7).

## Who needs to act

- Operators who saw refused autopilot `sync` jobs for Google/GitHub connector
  sources: no action — the churn stops on the next cycle.
- Operators with a connector source stuck on a stale `local_path`: run
  `gbrain sources set-path <id> --clear` once, then `gbrain doctor`.
- On persistence-managed installs, `set-path` delegates to the source
  lifecycle, which refuses `--clear` (`--clear does not apply to sources
  set-path`). A persistence-managed connector source that needs a cleared
  root currently has no lifecycle operation for it — the autopilot skip
  above still stops the refused-job churn on every install.

## Risk notes

- No schema migration. Clearing `local_path` never touches files on disk and
  does not affect the connector binding, which resolves its root from
  `persistence_host_bindings`, not `sources.local_path`.
